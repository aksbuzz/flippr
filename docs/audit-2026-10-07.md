# Flippr Review and Audit

- **Date:** 2026-10-07
- **Scope:** whole repository at commit `0dcef03` (management service and worker, evaluation service,
  React UI, JS SDK, `init.sql`, Docker Compose, docs)
- **Related:** [Architecture Decision Records](adr/README.md). Each finding below links to the ADR
  that records the decision it relates to.

## 1. Summary

Flippr has a sound core design: a control plane / data plane split, PostgreSQL as source of truth,
Redis as the evaluation cache, parameterised SQL, schema validation on every route, and a tidy
feature-folder layout. Static checks are clean.

However, the project **does not currently work end to end as documented**, several bugs silently
return wrong flag values, and it has **no authentication**. None of this is architectural; all of it
is fixable in small, targeted changes.

| Severity | Count | Meaning |
| --- | --- | --- |
| Blocker | 4 | The documented setup or main flow does not work |
| High | 16 | Wrong results, data integrity or serious security gap |
| Medium | 31 | Reliability, UX, maintainability and hardening gaps |
| Low | 21 | Polish and cleanup |

72 findings in total. Some overlap by design (UI-6 with H1, UI-10 with M3), because the UI and the
API each need their own fix.

### Verdict by area

| Area | State |
| --- | --- |
| Management service | Good structure. Build output is wrong; data-integrity and cache gaps. |
| Evaluation service | Small and correct for the happy path. No CORS, no graceful shutdown, no tests. |
| JS SDK | **Broken against the real API** (wrong URL). No timeout, no tests. |
| UI | Tidy prototype. Errors invisible, pagination ignored, hard-coded API URL. |
| Database | Good constraints. Missing uniqueness and no migration path. |
| Deployment | Management image cannot be built. Data stores exposed with default credentials. |
| Security | No authentication or authorization anywhere. |
| Process | No CI. Tests only for the management API. |

## 3. Blockers: the documented path does not work

### B1. The management image cannot be built or started

- **Where:** [`services/management/.dockerignore`](../services/management/.dockerignore),
  [`tsconfig.json`](../services/management/tsconfig.json) (`rootDir`, `include`),
  [`Dockerfile`](../services/management/Dockerfile) (`CMD`),
  [`package.json`](../services/management/package.json) (`start:server`, `start:worker`)
- **Problem:** two independent faults.
  1. `.dockerignore` lists `tsconfig.json`, so `RUN npm run build` runs `tsc` with no configuration
     and produces no `dist/`. The next stage then fails on `COPY --from=builder /app/dist`.
  2. Even with the config, `rootDir: "."` plus `include: ["src", "tests"]` makes `tsc` emit
     `dist/src/index.js` and `dist/tests/...`. The `CMD`, `start:server` and `start:worker` all run
     `node dist/index.js` or `node dist/worker/index.js`, which do not exist.
- **Fix:** remove `tsconfig.json` from `.dockerignore`. Use a separate `tsconfig.build.json` with
  `rootDir: "src"` and `include: ["src"]` (excluding tests), build with it, and keep the existing
  `dist/...` paths. Add `docker compose build` to CI.
- **ADR:** [0013](adr/0013-docker-compose-packaging-and-spa-ui.md)

### B2. The SDK calls a URL the server does not serve

- **Where:** [`sdk/js-sdk/src/index.ts:59`](../sdk/js-sdk/src/index.ts) vs
  [`services/evaluation/internal/api/route.go:16`](../services/evaluation/internal/api/route.go)
- **Problem:** the SDK requests `{baseUrl}evaluate/{flagKey}`. The server serves
  `GET /api/v1/evaluate/flags/{flagKey}`. With the README's `baseUrl: 'http://localhost:8080'` every
  call returns 404, which the SDK logs and converts into the caller's default. Applications run on
  code defaults with no visible failure. The flag key is also not URL-encoded.
- **Fix:** build the URL as `${baseUrl}/api/v1/evaluate/flags/${encodeURIComponent(flagKey)}`. Add an
  SDK test against a fake server and one cross-service contract test (see [T1](#7-tests-ci-and-process)).
- **ADR:** [0010](adr/0010-js-sdk-evaluation-and-caching.md)

### B3. New flags and environments are never written to Redis

- **Where:** [`projects.service.ts` `createFlag`](../services/management/src/features/projects/projects.service.ts)
  (line 82), [`worker/processor.ts`](../services/management/src/worker/processor.ts); the only Redis
  write is [`flags.service.ts:109`](../services/management/src/features/flags/flags.service.ts)
- **Problem:** `createFlag` and the worker insert `environment_flag_states` rows with
  `is_enabled = false` but never populate Redis. Until someone toggles that flag in that environment,
  the evaluation API returns `{"value": null}` instead of the flag's `off_value`. A new flag with
  `off_value: 100` evaluates to `null`, which the SDK turns into the application default.
- **Fix:** extract `syncFlagToRedis(flagId, environmentId)` from `updateFlagState` and call it on flag
  creation (for every environment) and when the worker links an environment.
- **ADR:** [0004](adr/0004-synchronous-write-through-to-redis.md), [0015](adr/0015-cache-reconciliation-and-redis-durability.md)

### B4. The worker container is reported unhealthy

- **Where:** [`docker-compose.yml`](../docker-compose.yml) (`management-worker`, lines 62 to 82),
  [`services/management/Dockerfile`](../services/management/Dockerfile) (`HEALTHCHECK`)
- **Problem:** the worker uses the same image, so it inherits the HTTP healthcheck on port 4000. The
  worker serves no HTTP, so Docker marks it `unhealthy` after the start period.
- **Fix:** override with `healthcheck: { disable: true }` in Compose, or check the process, or give
  the worker a tiny health endpoint.
- **ADR:** [0007](adr/0007-async-environment-linking-with-bullmq.md)

## 4. High severity

### H1. No authentication or authorization

- **Where:** [`services/management/src/index.ts`](../services/management/src/index.ts) (no auth
  middleware), UI `api-client.ts` (sends no credentials)
- **Problem:** anyone who can reach port 4000 can list every environment and its `sdk_key`
  (`GET /projects/:id/environments`), toggle any flag in any environment (including production), and
  create or alter data. The UI also displays every SDK key in plaintext.
- **Fix:** see the staged plan in [ADR 0014](adr/0014-management-api-authentication.md). The smallest
  useful step is a bearer token middleware on everything except `/health`.

### H2. Postgres and Redis are published with default credentials

- **Where:** [`docker-compose.yml`](../docker-compose.yml) (`postgres` ports and env, `redis` ports)
- **Problem:** `5432` and `6379` are exposed on all host interfaces. Postgres uses
  `flippr_user` / `flippr_password` and Redis has no password. Anyone on the network can rewrite flag
  values directly in Redis, bypassing the API entirely.
- **Fix:** bind to `127.0.0.1` or remove the host port mappings, set `requirepass`, move secrets to
  an `.env` file that Compose reads.

### H3. A flag can be served a variant that belongs to another flag

- **Where:** [`flags.service.ts` `updateFlagState`](../services/management/src/features/flags/flags.service.ts)
  (lines 55 to 118), schema `serving_variant_id` foreign key in [`init.sql`](../init.sql)
- **Problem:** `serving_variant_id` has a plain FK to `feature_flag_variants(id)` and the service
  never checks that the variant belongs to `flagId`. A request can point flag A at flag B's variant,
  or at a variant from another project, and the foreign value is cached in Redis.
- **Fix:** verify `variant.feature_flag_id = flagId` (404 or 400 otherwise). Better, make it
  structural with a composite FK `(feature_flag_id, serving_variant_id)` referencing
  `feature_flag_variants (feature_flag_id, id)`.
- **ADR:** [0006](adr/0006-flag-data-model.md)

### H4. `deleteVariant` can delete another flag's variant

- **Where:** [`flags.service.ts:40-53`](../services/management/src/features/flags/flags.service.ts)
- **Problem:** it checks that `flagId` exists, but the delete is `WHERE id = $1` with only the
  variant id. Any variant can be deleted through any valid flag's URL. Also, the "in use" check and
  the delete are not atomic, so a concurrent toggle produces a foreign-key error, which surfaces as a
  500 instead of a 400.
- **Fix:** `DELETE ... WHERE id = $1 AND feature_flag_id = $2`, return 404 when no row is deleted, and
  map the FK violation (`23503`) to a 400.

### H5. Duplicate project names are not prevented, and the 409 is dead code

- **Where:** [`projects.service.ts:15-29`](../services/management/src/features/projects/projects.service.ts),
  [`init.sql`](../init.sql) (`projects`, `environments`)
- **Problem:** `createProject` maps Postgres error `23505` to a 409, but `projects.name` has no
  unique constraint, so the branch can never run and duplicates are accepted. `environments` also has
  no unique `(project_id, name)`.
- **Fix:** add `UNIQUE (name)` on `projects` and `UNIQUE (project_id, name)` on `environments`, add
  tests for the 409s. This needs a migration path ([D1](#database)).

### H6. Redis loss silently turns every flag into its code default

- **Where:** [`docker-compose.yml`](../docker-compose.yml) (`redis`), evaluation `handler.go`
- **Problem:** the cache is the only data source for evaluation and nothing repopulates it. Default
  Redis persistence (RDB snapshots, no AOF) loses recent changes on a crash, and a flush or empty
  failover loses everything. A missing key returns `200 {"value": null}`, indistinguishable from "flag
  does not exist". The BullMQ queue shares the same instance.
- **Fix:** [ADR 0015](adr/0015-cache-reconciliation-and-redis-durability.md): a rebuild-from-Postgres
  job on start-up and on a schedule, `appendonly yes`, a separate Redis for queues, and a distinct
  signal for unknown keys.

### H7. The Redis write happens before the database commit

- **Where:** [`flags.service.ts:108-109`](../services/management/src/features/flags/flags.service.ts)
- **Problem:** the `SET` is inside `db.tx(...)` before the commit. If the commit fails, Redis holds a
  value Postgres does not, with no detection. The Redis latency also extends the row lock.
- **Fix:** write after the commit (and rely on the reconciliation job for the rare crash in between),
  or use a transactional outbox.
- **ADR:** [0004](adr/0004-synchronous-write-through-to-redis.md)

### H8. The evaluation API has no CORS support

- **Where:** [`services/evaluation/internal/api`](../services/evaluation/internal/api)
- **Problem:** there is no `OPTIONS` route and no `Access-Control-*` headers. A browser cannot call
  the API cross-origin, yet the README's SDK example sets `innerText` on a DOM element. Because the
  SDK also sends `Content-Type` and `Authorization`, browsers send a preflight that currently
  returns 405.
- **Fix:** add a CORS middleware with a configurable origin allowlist. Decide first whether browser
  use is supported, because it needs a client-side key type ([ADR 0005](adr/0005-sdk-key-as-environment-credential.md),
  [ADR 0014](adr/0014-management-api-authentication.md)).

### H9. SDK keys have no lifecycle and are one all-powerful key type

- **Where:** [`projects.service.ts:48`](../services/management/src/features/projects/projects.service.ts),
  [`init.sql`](../init.sql) (`environments.sdk_key`)
- **Problem:** the key is stored in plaintext, appears in Redis keys, the list API response and
  `rest.http`, and cannot be rotated or revoked (there is no environment delete or update endpoint).
  A key placed in browser code can read every flag value, including JSON configuration, for that
  environment. The key embeds the user-supplied environment name, which is neither validated nor
  length-limited, so a long name overflows `VARCHAR(255)` and fails with a 500.
- **Fix:** validate and limit names, hash keys at rest, add rotation, and split server and client
  keys. See [ADR 0005](adr/0005-sdk-key-as-environment-credential.md).

## 6. UI findings

These come from a read-only review of `ui/src` (paths relative to `ui/`). UI-4 and UI-9 were
re-checked by me.

### High

- **UI-1. API errors are never shown.** `src/lib/api-client.ts:11-15` swallows errors (the commented
  path `error.response.error` is wrong; the real one is `error.response.data.error`). Every create
  handler awaits `mutateAsync` without a catch, so a 400 or 404 becomes an unhandled rejection with
  no message, and the toggle has no `onError`. There is no `onError`/`isError` use anywhere in `src`.
  *Fix:* normalise errors in the interceptor, show `mutation.error` in dialogs, add a toast for
  toggles.
- **UI-2. Queries have no error branch.** `routes/flag.tsx:44` and the flag, environment and variant
  lists return `null` on error (blank page). `projects/components/list.tsx:17` shows "No projects yet"
  on a network error. `routes/root.tsx:6-8` shows a bare "Something went wrong!" replacing the whole
  layout with no retry. *Fix:* render an error state with a Retry button, and a real empty state.
- **UI-3. Pagination is ignored.** The API defaults to 20 items (max 100). The project, flag and
  environment queries never send `limit` or `offset` and drop `pagination` from the response, so item
  21 onwards is invisible and unmanageable. *Fix:* add a `Paginated<T>` type and page controls.
- **UI-4. Route loaders never run (rated Medium, listed here because it is a one-line fix and
  counted under Medium).** `routes/{flags,flag,environments}.tsx` define
  `clientLoader = qc => () => async ({params}) => ...`, with an extra `() =>`. `convert` in
  `app/router.tsx:13-21` sets `loader: clientLoader(queryClient)`, so the loader returns a function and
  never fetches. No prefetch, so every page spins after render. *Fix:* remove the extra `() =>`.
- **UI-5. API URL is hard-coded.** `src/lib/api-client.ts:3-5` uses `http://localhost:4000/api/v1`
  compiled into the bundle, and the API's CORS list is localhost-only, so the UI works only from a
  browser on the Docker host and breaks behind HTTPS (mixed content). *Fix:* default to a relative
  `/api/v1`, add `location /api/ { proxy_pass http://management-api:4000; }` to `nginx.conf`, and
  optionally `VITE_API_URL`.
- **UI-6. No auth handling, and SDK keys shown in plaintext.** `features/environments/components/list.tsx:38-41`.
  *Fix:* see [H1](#h1-no-authentication-or-authorization). Mask keys by default.

### Medium

- **UI-7. Double submit.** `components/ui/Button.tsx:41-49`: `isLoading` shows a spinner but does not
  set `disabled`, so a double click creates duplicates.
- **UI-8. Stale flags list after a toggle.** `flags/api/update-flag-state.tsx:44-46` invalidates only
  the single flag, so the "Enabled in x/y environments" chip stays stale for the 60 s `staleTime`, and
  `refetchOnWindowFocus: false` (`app/provider.tsx:14`) prevents self-healing.
- **UI-9. Selecting a variant silently enables the flag.** `flags/components/environments-mapping.tsx:26-32`
  sends `is_enabled: true` when a serving variant is chosen on a never-configured environment, which
  turns the flag on live, possibly in production. *Fix:* separate "choose variant" from "enable", or
  require a confirmation.
- **UI-10. Creating an environment does not refetch flags.** `environments/api/create-environments.tsx:35`.
  Combined with the async linking ([M3](#management-service)), the Environment Mapping tab goes stale
  and a toggle can hit a 404 that is not displayed.
- **UI-11. One shared mutation for every mapping row.** No pending state, controlled values only move
  after the PATCH and refetch, failures revert silently, rapid clicks interleave.
- **UI-12. Cells remount on every render.** `components/ui/DataTable.tsx:45` renders `<column.Cell/>`
  with an inline function, giving a new component identity each render. The switch and select lose
  focus during mutation re-renders. *Fix:* use a render function instead of a component.
- **UI-13. Validation differs from the API.** `features/{flags,variants}/api/create-*.tsx` validate
  numbers with `Number()`, while the API uses `JSON.parse`. `.5` or `007` pass the UI and fail the API
  (invisible, see UI-1); `json` type rejects arrays the API accepts; `string` rejects `""`.
- **UI-14. nginx has no security headers.** No CSP, `X-Frame-Options`/`frame-ancestors`,
  `X-Content-Type-Options`, `Referrer-Policy`, and `server_tokens` is on. The static-asset `location`
  has its own `add_header`, which would also hide server-level ones. *Fix:* shared include repeated per
  location.
- **UI-15. nginx caching.** A six-month expiry applies to every static extension (not only hashed
  assets) and `index.html` has no `Cache-Control: no-cache`, so a stale `index.html` can reference
  deleted assets after a deploy. `error_page 404 /index.html` is redundant and returns HTML for
  missing JS. *Fix:* `location /assets/ { expires 1y; add_header Cache-Control "public, immutable"; }`
  and `no-cache` for `index.html`.
- **UI-16. Dockerfile.** `npm install` rather than `npm ci`, floating tags, nginx runs as root, no
  build-time API URL argument, healthcheck uses `localhost` (may resolve to `::1`, not confirmed).
- **UI-17. Types do not match the API.** `src/types/api.ts`: `created_at: Date` is really a string;
  `off_value` and `value` are typed `string` but are parsed JSONB; `serving_variant_id` is really
  nullable; `FeatureFlagsResponse` claims fields the list endpoint omits; the Axios interceptor returns
  `response.data` but the API functions are typed over `AxiosResponse`. (The UI works today only
  because it applies `JSON.stringify` when rendering. This is not a double-encoding bug.)
- **UI-18. Forms are not forms.** `components/ui/FormDialog.tsx:80-89` has no `<form>`, so Enter does
  nothing and `type="submit"` buttons are inert. Field components never pass `invalid` or
  `aria-invalid`, and error text has no `role="alert"`.
- **UI-19. Accessibility names.** Icon-only buttons have no `aria-label`
  (`flags/components/list.tsx:68-75`, `projects/components/create.tsx:39-41`). `CopyButton.tsx` is an
  unfocusable `<svg onClick>` and shows success even when the clipboard API is unavailable
  (non-HTTPS origins). Mapping-row selects and switches are unlabelled.

## 9. What is good

- Clean control plane / data plane split with a small, fast read path ([ADR 0002](adr/0002-control-plane-data-plane-split.md)).
- Parameterised SQL everywhere (no injection found), Zod validation on every route, strict TypeScript.
- Meaningful database constraints, including `enabled_requires_variant` and unique keys per scope.
- Idempotent worker job (`ON CONFLICT DO NOTHING`) and a row-lock that serialises concurrent toggles.
- A fail-safe SDK (always returns a usable value) with no runtime dependencies.
- Real integration tests with Testcontainers rather than mocks ([ADR 0012](adr/0012-integration-tests-with-testcontainers.md)).
- Consistent feature-folder structure on both the backend and the UI, with stable query keys.
- All static checks pass and the SDK builds.
